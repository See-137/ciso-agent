# ADR-0013: Audit integrity (hash-chained append-only log with a keyed, two-phase head anchor and an optional head witness)
Status: Proposed (reversible default; owner approval pending)
Date: 2026-11-17
Revised: 2026-11-18 (two-phase anchor and crash recovery, log id, witness, placement rules, residual risks)
Blueprint refs: §5.1 #14, §8.4 step 6, §9.2, §9.5, §11 (audit tampering row), §19.2, §19.3 (resilience: audit integrity), §19.4 #4, FR-028, NFR-006, NFR-016, NFR-017, OD-01, OD-17; plan gaps G4, G5

## Context
The BP requires "tamper-resistant audit storage separate from agent write permissions" (§5.1 #14), "correlatable, time-stamped, tamper-evident records" (NFR-006), and, against audit tampering, "append-only or tamper-evident event storage; separate writer identities; restricted delete permissions; backups and integrity checks" (§11). The model cannot delete audit records (§9.2). A write action must fail closed when the audit path is unavailable (§9.5). An unkeyed hash chain with triggers does not show that records were cut off the end, and anyone who can write the file can drop the triggers and recompute every hash (plan gap G4). The audit and operational databases are separate files, so no transaction spans both (G5).

## Options considered

| Option | Gains | Costs | Security impact |
|---|---|---|---|
| Hash chain, append-only triggers, and an HMAC-keyed head anchor in a file outside the audit database, on the same host | Detects edits inside the chain, tail truncation and a full recompute by someone who lacks the key; no extra service | One more file and one key to protect and back up; an anchor that disagrees with the log stops all appends | Tamper-evident against an attacker with file access and no key. Not against one who has the key, and not against a rollback of both files |
| Unkeyed chain and triggers only | Simplest | Tail truncation and full recompute go unnoticed | Rejected (G4) |
| External anchoring: copy the latest (sequence, hash) to a place this host's accounts cannot write | Detects rollback, wipe and a rewrite by a key holder, after the last copy | Needs an independent location and a routine that compares against it | Closes the main remaining gaps. Built as an optional witness file whose location is a setting; no such location exists yet (OD-01), so it is not on by default |
| Per-record signatures with a key held outside the application process | Forgery needs a key the process never sees | Needs a separate signer process or hardware | Strong once processes are split (ADR-0010) |
| Write-once storage from the host or a storage service | Deletion is blocked below the application | Depends on host and product choices that are open (ADR-0015) | Strong against the application's own compromise |

## Default chosen for the local build
`ciso.audit` (`log.py`, `anchor.py`, `reconcile.py`, `witness.py`, `chain.py`, `verify.py`, `tables.py`):

The log
- The log has its own database file (`data_dir/db/audit.db`) and its own table metadata. Triggers abort UPDATE and DELETE on records and on the identity row, and abort an INSERT whose `seq` or `prev_hash` does not follow the current head. The log class has no update or delete method.
- A record's `hash` is SHA-256 over the canonical JSON of every other field, including `prev_hash`. `seq` is gapless from 1. `details` must be JSON-native (anything else is refused, not turned into text) and passes through the redactor before it is hashed; if redaction fails, the append is refused. What is stored is exactly what is hashed, and `verify()` rejects a row whose stored text differs, so a duplicate key, a non-canonical spelling or a rewritten timestamp is a failure.
- Log id and explicit initialisation. `initialise()` runs once on a new log. It creates a random `log_id`, kept in a write-once row of the database and in the anchor under the HMAC. It refuses if the database has records or an identity, if an anchor file exists, or if the object was given an expected id. An uninitialised log refuses appends. The composition root remembers the id in the operational database and passes it back as the expected id on every start. A log that was wiped is never re-initialised: the platform refuses to append and reports it. A log wiped and re-created has a different id and verifies as failed.

The anchor
- The anchor is a small JSON file outside the audit database holding a format version, the key id, the log id, the final head (`seq`, hash), an optional pending head and an HMAC-SHA256 over them with a domain label. The key is resolved from a `secret://` reference (`audit_hmac_key_ref`). The key id is a hash that names the key without revealing it, so an anchor signed with another key reads as a key mismatch and not as tampering. Writing is atomic: temporary file, fsync, rename, with a bounded retry while another handle holds the file (Windows), and a directory fsync where the platform offers one.
- Two-phase append. An append takes the database write lock, reconciles the head with the anchor, inserts the record, writes the anchor with the new head as `pending`, commits, then promotes `pending` to `final`. It returns a receipt for a committed, anchored record or it raises. A caller that gets an exception must not perform its side effect.
- Crash recovery is automatic and covers two signatures only. `commit_not_applied`: the anchor has a pending head and the database head is still the final one, so the transaction never committed and the pending entry is dropped. `promotion_missing`: the database head is exactly the pending head and the record at the final position still has the final hash, so the commit happened and the promotion did not; pending is promoted. The next `open`, append or verify repairs either state and writes an `audit.anchor_recovered` record naming the case, before any new record. A failed promotion after a successful commit is not raised; the receipt is returned and the next writer repairs it. Any other mismatch is refused and never repaired.
- An append is refused when the log is uninitialised, the log id differs, the anchor is missing for a non-empty log, unreadable, forged or signed with another key, the key is unavailable, or the head and the anchor disagree in a way that is not one of the two crash signatures (`truncated`, `anchor_hash_mismatch`, `anchor_behind_head`).
- `verify()` walks the whole chain in a read snapshot without blocking appends, then takes the write lock briefly to walk what was added since, reconcile head and anchor, and check the witness. It returns `ok` only when the chain is intact, the anchor is present, valid and equal to the head, and any configured witness agrees. It returns `failed` for a sequence gap, a hash or link mismatch, an invalid row, an anchor ahead of the head (`truncated`), an anchor hash mismatch or a bad MAC, an anchor behind the head (a record added without the key), a log id mismatch, a missing identity row, and `rolled_back` or `witness_invalid` from the witness. It returns `unverifiable`, never `ok`, when the anchor or key is missing or unreadable, the anchor is signed with another key, the log is uninitialised, the witness cannot be read, or another process's crash state keeps appearing. The result says whether a witness was consulted (`witnessed`).

The witness (optional)
- `FileHeadWitness` is an append-only JSON-lines file with one HMAC-signed line per published head (log id, `seq`, head hash, time), signed with its own key (`audit_witness_key_ref`, a different secret from the anchor key). `AuditLog` publishes after commit every `audit_witness_every` records (a safety setting). With a witness the cadence is required.
- Before every append the log checks the witness. If the chain no longer contains the latest witnessed head, the append is refused (`rolled_back`), so the log's own writer never grows a rolled-back chain past the witnessed point and hides the rollback. Two different heads recorded for one `seq` are `witness_invalid`. An unreadable witness refuses appends (fail closed). If publishing fails after the commit, the append raises `FailClosed` although the record is committed, and the caller must still not perform its side effect.
- Wiring status: the settings exist (`audit_witness_path`, `audit_witness_key_ref`, `safety.audit_witness_every`), and `config/provisional-settings.json` sets the cadence only. The composition root does not yet pass a witness to the log; wiring it is in progress. Until then readiness warns that the log is not witnessed, and `verify()` reports `witnessed` false. A witness path set in settings today is reported as not wired.

Placement
- `AuditLog` refuses to be built with an anchor or a witness anywhere under the audit database's own directory (`data_dir/db/`), subdirectories included, because whoever can restore or replace the database there rolls the anchor back with it. In that case the composition root runs with an audit log that refuses every call and reports the setting as missing.
- The default anchor is `data_dir/anchor/audit-head.json`. It is outside the database directory and so accepted, but it is still under the data directory, so whoever can write that directory can roll back the database and the anchor together. Readiness reports this as a warning (`audit anchor is stored under the data directory`). The `audit_anchor_path` setting moves it. The witness has no default location; with none, the log is unwitnessed. The provisional settings file sets neither path.

What the anchor does protect against: edits, deletions and renumbering inside the chain; tail truncation; a full recompute of the chain by someone without the key; a record added without the key; a forged or replayed anchor on its own; a log swapped for another log.

What the anchor does not protect against, and the residual risks:
- Anyone who holds the HMAC key and can write the files can rewrite history and produce a matching anchor. In this build the key is resolved inside the same process that runs everything else.
- Without a witness, replacing the database and the anchor with an older pair that once matched verifies as `ok`. This needs file access only, not the key. Removing exactly the records of the last transaction together with rolling the anchor back to its earlier bytes looks the same as a commit that never happened. No anchor kept on the same host can tell these cases apart.
- A witness narrows this and does not remove it. It helps only if its storage cannot be changed by whoever can write the data directory (another host, a write-once share, a different operating-system identity). Records written after the last published head can still be rolled back unnoticed, which is up to the whole cadence window when the cadence is more than one. A missing or empty witness file reads as a witness that has not seen the log, not as an error, and a witness cut back to an older prefix hides a rollback to that point. Someone with both keys and write access to the witness storage can forge it. The witness proves a head existed; it does not prove the records are right.
- A legitimate restore is also a rollback. The restore check verifies the restored log against its own restored anchor and cannot tell the difference (ADR-0014).
- If the operational database that remembers the log id is wiped together with the audit database and the anchor, nothing remembers the log, and it can be initialised afresh.
- A crash during `initialise()` can leave the anchor written and the identity row missing, and a crash while appending to the witness can leave a torn last line; the log then refuses to open or append and there is no tool for either state. Recovery from both is in progress.
- A key rotation is not built. After a rotation every anchor reads as a key mismatch and appends are refused until the log is re-anchored, and no re-anchor tool exists.
- A log that refuses appends stops everything that audits first: policy evaluation for writes, inference calls, kill-switch release, identity changes, backup and restore, and state-changing API requests. Sign-in, reading and verification still work (ADR-0004), and engage still works (ADR-0018).
- The composition root opens the log (identity, anchor, witness, crash repair) at start-up but does not walk the chain. A walk runs through `python -m ciso.app.admin audit-verify`, `GET /v1/audit/verify`, or `ciso.ops.startup`, which is built and not yet called by the composition root (ADR-0014).
- The audit writer is the same OS identity as everything else, so "separate writer identities" (§11) is not met.
- A secret the redactor misses stays in an append-only log. Append-only storage may also conflict with a deletion duty found later (OD-17, OD-10).

## Why this default is reversible
Seam: callers depend on the `AuditSink` protocol (`append`); `AuditLog` adds `verify` and `query`; `HeadAnchor` takes a path and a key reference. External anchoring is already an option through the witness: it exports signed heads to another location and compares them later; the record format does not change. Moving the anchor itself off the host would replace the file with a call to that location. Per-record signing adds a field and a format version. Moving to another store means replaying records in order and verifying the result.

## Evidence needed to make this final
- Where the witness and the anchor can live, outside the data directory and outside the reach of the account that writes the audit database, and which account may write them (OD-01). Until the owner decides, both are "not isolated" and readiness says so.
- Where the HMAC keys are held and how they are recovered (ADR-0008), and how a key is rotated without losing verifiability.
- A procedure for the states that have no tool today: a failed initialise, a damaged witness, a rotated key. Who may run it, what evidence it requires, how it is recorded.
- Retention schedules and any deletion duties (OD-17, OD-10); audit expectations from customers (OD-10).
- Which identity writes audit records after the process split (ADR-0010).

## Consequences
- The append-only audit path exists before any write-capable tool, as BP §19.4 #4 requires.
- `verify()` must run at start-up, on a schedule and after every restore; its result belongs in operator reporting. Today only the manual commands and the API route run it.
- The anchor file, the witness file and the HMAC keys must be backed up and restored with, or alongside, the audit database (ADR-0014). The witness should not be restored from the same archive: its value is that it is kept apart.
- The integrity claim that can be made to an outside reviewer is limited to this: tampering by someone without the keys is detected; a rollback of the database and anchor together is detected only up to the last head a witness holds, and only if a witness is configured on storage the attacker cannot write.
