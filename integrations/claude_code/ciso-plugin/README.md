# CISO agent plugin for Claude Code (no servers)

One plugin the organization adds through its marketplace and force-enables through
managed settings. It contains:

1. **Enforcing hooks** (`hooks/hooks.json`): every tool call (`PreToolUse`, matcher `*`)
   and every prompt (`UserPromptSubmit`) is decided on the engineer's machine, BEFORE it
   runs, by the same governance engine, inspector and hook intake as the optional
   AI-governance service, with the bundled ruleset. No model decides. No server.
2. **The CISO skill** (`skills/ciso/`): a CISO agent the engineer or the security lead
   invokes (`/ciso-agent:ciso`). It reviews code, diffs, PR ranges and whole repositories,
   explains verdicts, audits agent setups, summarises local findings and decisions, and
   answers AI-use questions. **It advises; the hooks enforce.**

The service, the sandbox and the managed policy pack elsewhere in this repository stay
an optional add-on; nothing here needs them.

## Layout

| Path | What it is |
|---|---|
| `.claude-plugin/plugin.json` | Manifest, plugin `ciso-agent` (id `ciso-agent@corp-ai-governance`) |
| `hooks/hooks.json` | The two enforcing hooks: exec form (no shell), `timeout: 60`, `onFailure: "block"` |
| `scripts/ciso_hook.py` | Hook entry: runs the runtime guard, then `lib/ciso_plugin/hookio.py` |
| `scripts/runtime_guard.py` | Standard-library guard loaded by path before the bundle: refuses an interpreter that is not uv's own isolated environment (review H1) |
| `scripts/runtime-requirements.txt` | The five runtime packages, pinned with SHA-256 hashes (see "Machine requirements" for what uv does with them) |
| `scripts/no-local-packages/` | Empty on purpose: passed to uv as `--find-links` so `UV_FIND_LINKS` cannot add a package source |
| `lib/ciso/` | GENERATED byte-for-byte copy of `ciso.governance`, `ciso.inspection`, `ciso.intake`, `ciso.app.change_shape`/`change_decide` and exactly what they import (`tools/build_ciso_plugin.py`; `--check` fails on any drift). `ciso/app/__init__.py` is a fixed stub |
| `lib/BUNDLE.json` | Generated manifest: copied files and their SHA-256 |
| `rules/governance-ruleset.json` | GENERATED: `config/governance-ruleset.provisional.json` plus the plugin's additions (`PLUGIN_ADDITIONS` in the build tool): the assistant's credential files (`.claude.json`, `.claude/.credentials.json`, the platform SDK profile folders) as credential paths, and the uv cache and uv Python folders as protected configuration |
| `lib/ciso_plugin/` | The plugin's own code: settings, local identity, audit and findings logs, safe git, push scan, own-tool recognition, the decision flow, messages, the skill tools |
| `skills/ciso/SKILL.md` | The skill (focused); detail in `skills/ciso/references/*.md` |
| `skills/ciso/scripts/ciso_tool.py` | The skill's read-only tool: `review`, `check`, `audit-setup`, `summary` |
| `apps-skill/SKILL.md` | The Claude apps edition of the skill (no scripts), packed into the apps zip |

Managed settings templates and their checker: `../managed-plugin/`.

## How a decision is made (local mode)

1. The hook payload is normalised exactly as the service does (`ciso.intake.hook`).
   Command and content are classified and inspected as written (the intake's redactor is
   a pass-through here) and never stored.
2. **Attribution, local mode**: the person is the operating-system account the hook runs
   as, read from the OS (`GetUserNameExW` on Windows, the password database elsewhere),
   with the role from `CISO_ROLE` (default `employee`). On a managed device that account
   counts as `verified`, reason `local_os_account`. **This trusts the device's login: there
   is no central identity.** If the account cannot be read, attribution is `unknown` and
   every non-read action is denied. Agent class: `employee_operated`, or `organizational`
   when `CISO_AGENT_CLASS` says so (company bots running the plugin).
3. The plugin's own skill (the `Skill` tool naming `ciso-agent:ciso`; a bare `ciso` is a
   project or user skill and goes to the engine) and its tool in the exact documented
   command shape are allowed and audited (`lib/ciso_plugin/selfcmd.py`), but only for a
   verified account with a valid role; while the stop flag is engaged only loading the
   skill and `summary` (which write nothing) are allowed this way, and everything else
   goes to the engine, which denies it.
4. Inspection with the bundled `Inspector`: file writes and edits (path and content),
   prompts, shell commands (write targets, secrets, risky code), sub-agent prompts.
   Pushes and commits: see below.
5. Decision with the bundled `GovernanceEngine` and ruleset. Local implementations of
   its dependencies: system clock; kill switch = the organization stop flag
   `CISO_STOP` (anything not clearly off counts as on; blocks every non-read action);
   principals = the logged-in account with the configured role.
6. Records, in the plugin's per-user data directory (`${CLAUDE_PLUGIN_DATA}`, i.e.
   `~/.claude/plugins/data/<id>/`):
   - `audit/decisions.jsonl`: append-only, SHA-256 hash-chained JSON lines (the engine's
     `governance.decide` record and the plugin's `ciso.plugin.result` record per
     decision): decision id, verdict, reason codes, rule ids, action kind, tool, redacted
     target, content hash and size, finding ids. Never command text, prompts or content.
   - `findings/findings.jsonl`: the findings (rule, severity, fixed detail and
     remediation, redacted location), same chain.
   - `reports/`: reports the skill's tool writes.
   A writer lock keeps parallel hooks on one chain. If any record cannot be written, the
   BEFORE action is denied.
7. Answer: allow prints nothing (Claude Code's own permission rules still apply); deny
   and ask become `permissionDecision` with a message that names what was found, never
   the secret, and ends with `(CISO decision dec_...)`; a prompt that is denied or asked
   is blocked (`suppressOriginalPrompt`). Any failure exits 2 with a fixed message, and
   the hooks are `onFailure: "block"`, so a crash, a missing runtime or a timeout blocks.

## Pushes without a sandbox

On a `git push` the hook resolves exactly what will be sent and scans it
(`lib/ciso_plugin/pushscan.py`):

- Only one plain `git push <remote> <branch>` (or `<src>:<dst>`, `HEAD:<dst>`) naming a
  configured remote is scanned (`ciso.app.change_shape`). Anything else (bare `git push`,
  `--force`, `--all`, `--tags`, `--mirror`, deletes, refspec lists, chains) is denied with
  a message saying how to push. Force pushes and pushes to protected branches are decided
  by the rules first (deny / ask) without scanning.
- The scan never follows settings that re-root it: the repository found from the hook's
  `cwd` must be plain, its git folder exactly `<top>/.git` where `<top>` is what
  `git rev-parse --show-toplevel` reports. `core.worktree` (any scope), `core.bare`, or a
  `.git` file (a `gitdir:` redirect, so also linked worktrees and submodule checkouts)
  refuse the push or commit scan with note `repo_layout`; push or commit those yourself.
- Refused with a message, before anything is scanned. The message lists fixed reason
  codes, never a config key or value:

  | Reason code | Setting |
  |---|---|
  | `remote_push_refspec`, `remote_mirror`, `remote_push_url`, `remote_receive_pack`, `remote_upload_pack` | `remote.<name>.push`, `.mirror`, `.pushurl`, `.receivepack`, `.uploadpack` |
  | `remote_second_url` | more than one `remote.<name>.url` (git pushes to every url; the scan base comes from the first) |
  | `url_push_instead_of` | any `url.*.pushInsteadOf` |
  | `git_proxy` | `core.gitProxy` |
  | `ssh_command`, `askpass_program`, `credential_helper` | repository-level `core.sshCommand`, `core.askPass`, `credential.*helper` |
  | `submodule_push` | `push.recurseSubmodules` / `submodule.recurse` that push submodules |
  | `hooks_path_in_repository` | `core.hooksPath` inside the repository |

  Hook programs (non-`.sample` files) in the repository's hooks folder refuse it too
  (`repo_hooks`).
- Scan base: `git ls-remote --heads <remote>` (git contacts the remote the push contacts
  anyway; Python opens no connection). An advertised tip is a base only when the local
  tracking ref `refs/remotes/<remote>/<branch>` holds the same commit, so neither a lying
  remote nor a moved local ref alone can shrink the scan. With no usable base the range
  runs to the root. More than 1000 commits: denied.
- Every commit in the range is inspected on its own (`git log -p`, merges against their
  first parent, no renames, no textconv), so a secret added and later deleted is found.
  Binary changes make the result incomplete and the push is denied.
- git is run safely: absolute git (`CISO_GIT_PATH`, else the first git on the absolute
  entries of `PATH`), fixed argv, no shell, stdin closed, per-step timeout, output cap,
  `--no-replace-objects`, fsmonitor off, hooks path pointed at a folder that never exists,
  no external diff, `--no-textconv`, `safe.bareRepository=explicit`, diff prefixes and
  relative mode fixed, every `GIT_*` variable dropped, every transport refused except for
  the one `ls-remote` (which still refuses `ext::`).
- `git commit -m <message>` is scanned the same way (the staged change).
- **Tests are not run.** There is no sandbox here; the optional sandbox add-on is where
  tests run. The skill says so too.

## Machine requirements

- Claude Code 2.1.316 or later (the templates set `requiredMinimumVersion`;
  `onFailure` needs 2.1.295+).
- **uv** on `PATH` (https://docs.astral.sh/uv/). The hooks run (exec form, no shell)
  `uv run --quiet --isolated --no-config --no-project --no-env-file --python ">=3.13"
  --default-index https://pypi.org/simple --index https://pypi.org/simple --find-links
  <plugin>/scripts/no-local-packages --index-strategy first-index --keyring-provider
  disabled --no-build --directory <plugin> --with-requirements
  <plugin>/scripts/runtime-requirements.txt -- python -I -B <plugin>/scripts/ciso_hook.py`.
  Why each flag (uv CLI reference, https://docs.astral.sh/uv/reference/cli/, fetched
  2026-11-19, and measured with uv 0.9.26):
  - `--isolated`, "Run the command in an isolated virtual environment": uv uses neither
    `VIRTUAL_ENV` nor a `.venv` in the plugin folder or any parent (measured: without it,
    a `.venv` above the plugin or `VIRTUAL_ENV` holding a `.pth` that ends the process
    turns every hook into a silent allow; with it the hook decides, review H1).
  - `--no-config` ("Avoid discovering configuration files (`pyproject.toml`, `uv.toml`)"),
    `--no-project` ("Avoid discovering the project or workspace"), `--no-env-file`
    ("Avoid reading environment variables from a `.env` file"), `--directory`: nothing
    near the repository the agent works in is read.
  - `--default-index`, `--index`, `--find-links <empty folder>`, `--index-strategy`,
    `--keyring-provider disabled`: a value on the command line replaces the variable
    (`UV_DEFAULT_INDEX`, `UV_INDEX_URL`, `UV_INDEX`, `UV_EXTRA_INDEX_URL`,
    `UV_FIND_LINKS`, `UV_INDEX_STRATEGY`, `UV_KEYRING_PROVIDER`). Measured for each with
    a closed local port: uv only tried the index given on the command line.
  - `--no-build`: a source distribution is never built (no build backend runs).
  - `-I` for Python: no `PYTHONPATH`, user site or working directory.
- **The runtime guard** (`scripts/runtime_guard.py`) then refuses (exit 2) unless the
  interpreter is 3.13+, isolated, runs in an environment uv created in its cache
  (`builds-v0` / `archive-v0`), imports only from the standard library or that uv cache
  (never the base interpreter's `site-packages`, a project venv or `src`), the uv folders
  on the path hold no `.pth` other than the two uv writes itself, and no `sitecustomize`
  was loaded.
- **Package hashes**: `scripts/runtime-requirements.txt` pins every package with SHA-256
  hashes (pydantic-core: the CPython 3.13 and 3.14 wheels for Windows x64/arm64, macOS
  x86_64/arm64, Linux manylinux/musllinux x86_64/aarch64), copied from uv's cached copy
  of the PyPI simple index on the build machine (no download, nothing installed).
  **Measured: `uv run --with-requirements` does NOT verify them** (a rebuilt wheel with a
  different hash was installed; `uv pip install --require-hashes` refused the same wheel),
  and `uv run` has no `--require-hashes` (that setting is for `uv pip` only). So the pin
  fixes versions and the index, not the bytes: whoever can serve or intercept `pypi.org`
  for this machine (for example through a root certificate the user trusts) can still
  supply the hook's packages. The binding option is the admin-installed runtime below.
- **Python 3.13 or later**, found or installed by uv.
- The pinned packages: pydantic 2.14.0, pydantic-core 2.50.0, typing-extensions 4.16.0,
  annotated-types 0.8.0, typing-inspection 0.4.5. Nothing else is imported (the build
  refuses any other third-party import). uv fetches them once from PyPI, then serves them
  from its cache; for machines without index access, pre-fill the uv cache and set
  `UV_OFFLINE=1` in the managed `env`.
- git (any recent version with `--diff-merges`, 2.31+), at `CISO_GIT_PATH`.
- If uv is missing, Claude Code cannot start the hook and blocks every tool call and
  prompt (`onFailure: "block"`), showing the hook error that names `uv`. If uv runs but
  Python 3.13+ or the packages cannot be provided, the hook blocks with: "the security
  check has no usable runtime ... IT must install uv and let it provide Python 3.13 or
  later with the plugin's pinned packages".
- Fallback when uv cannot be used at all, and the only option that binds the package
  hashes: none is shipped. The sound option is for IT to install Python 3.13 in an
  admin-owned folder, install the packages there with `uv pip install --require-hashes -r
  scripts/runtime-requirements.txt`, and change the hook `command` to that interpreter
  (`-I -B <plugin>/scripts/ciso_hook.py`); that is a plugin change (the runtime guard
  would have to accept that folder), not a setting.

## How an organization installs it (step by step)

1. **Host the marketplace.** Put `integrations/claude_code/` (this plugin, the
   `.claude-plugin/marketplace.json` that lists it) in a company git repository that every
   engineer can read.
2. **Build and check** from the repository root:
   `uv run python tools/build_ciso_plugin.py --check` (expects `bundle current`).
3. **Fill the managed settings template.** Edit
   `integrations/claude_code/managed-plugin/source.json`: the marketplace git URL (both
   places), the organization UUID, and per platform the admin-owned empty hooks folder
   and git path if they differ. Rebuild (`uv run python tools/build_ciso_plugin.py`),
   then `python integrations/claude_code/managed-plugin/check_managed.py
   integrations/claude_code/managed-plugin integrations/claude_code/ciso-plugin`. Deploy
   only on `RESULT: READY`.
4. **Prepare each machine** (endpoint management): install uv and git; create the empty,
   admin-owned hooks folder named in the template (Windows `C:\Program Files\CISOAgent\empty-hooks`,
   macOS `/Library/Application Support/CISOAgent/empty-hooks`, Linux
   `/usr/local/share/ciso-agent/empty-hooks`); optionally pre-fill the uv cache.
5. **Deliver the managed settings** for the platform
   (`managed-plugin/<platform>/managed-settings.json`): Windows `C:\Program Files\ClaudeCode\managed-settings.json`
   or the HKLM `Settings` registry value (`HKLM\SOFTWARE\Policies\ClaudeCode`); macOS the
   `com.anthropic.claudecode` profile or `/Library/Application Support/ClaudeCode/managed-settings.json`;
   Linux `/etc/claude-code/managed-settings.json`. If the organization also uses
   server-managed settings from the admin console, either put the same keys there or set
   `managedSourcesBehavior: "merge"`: by default the first managed source with a policy
   key wins.
6. **Confirm on one machine**: `/status` shows the managed source; `/plugin` lists
   `ciso-agent@corp-ai-governance`; `git push --force origin main` is refused with
   `(CISO decision dec_...)`; `/ciso-agent:ciso summary` shows the decision.
7. **Set the stop flag** when needed: change `CISO_STOP` to `"1"` in the managed `env`
   and redeploy (MDM and file sources are re-read on start and every 30 minutes).

What the template sets: the marketplace (`extraKnownMarketplaces`), the force-enabled
plugin (`enabledPlugins`), only that marketplace allowed (`strictKnownMarketplaces`),
`allowManagedHooksOnly: true` (user, project and other plugins' hooks are blocked;
hooks of plugins force-enabled in managed `enabledPlugins` still run, per the settings
reference), `disableSideloadFlags`, `disableCommandPluginSources`,
`disableBypassPermissionsMode`, deny rules for the agent's edits of plugin and settings
files and reads of common credential files, the company login, the minimum version,
`CISO_STOP`, `CISO_ROLE`, `CISO_AGENT_CLASS`, `CISO_GIT_PATH`, `UV_NO_CONFIG`, and the git
hardening for the agent's own git through `GIT_CONFIG_COUNT`/`KEY_n`/`VALUE_n`:
`core.hooksPath` to the empty admin-owned folder, `safe.bareRepository=explicit`,
`push.recurseSubmodules=no`, `protocol.ext.allow=never`, `core.fsmonitor=false` (an
allowed `git status` would otherwise run a repository's fsmonitor program, review L1).
The deny rules also cover reads of the assistant's credential files
(`~/.claude/.credentials.json`, `~/.claude.json`, any `.credentials.json`, the platform
SDK profile folders) and edits of the uv cache and uv Python folders.

`check_managed.py` is positive (review M4): it accepts only templates whose every security
key has exactly the expected value (the full deny list, minimum version 2.1.316, exactly
one marketplace, managed hooks only and none of its own, the plugin force-enabled, no
`dontAsk`/`bypassPermissions` default mode, no broad allow rule, the git hardening keys
each exactly once compared case-insensitively with no other `GIT_CONFIG*` variable, no
environment keys differing only in case, and the plugin's hooks running exactly the
declared uv argv).

## Claude apps (chat, Cowork)

`uv run python tools/build_ciso_plugin.py --zip dist/ciso-skill.zip` writes the skill
alone as a zip with one folder, `ciso/` (`SKILL.md` from `apps-skill/`, plus
`references/`). An Owner uploads it at Organization settings > Plugins & skills > Add >
Upload a skill; it takes effect for everyone, and users can switch provisioned skills off
for themselves. Skills need "Cloud code execution and file creation" and "Skills" on.

What works there, from the documentation: the instructions and references. The scripts
are left out on purpose: the bundled engine needs Python 3.13+ and pydantic, the
documented code execution container is Python 3.11 with a fixed package list that does
not include pydantic, and the claude.ai help pages do not document the Python version
or packages of the apps' environment. Nothing is enforced in the apps by this skill.

## Known limits, stated plainly

- **User-space plugin.** The plugin cache (`~/.claude/plugins/cache/...`), its data folder,
  uv and its cache live in folders the user can write. A user (or an agent the rules let
  run arbitrary code) can edit the hook code, the bundled rules or the logs. The managed
  deny rules and the engine's `agent_config_change` invariant stop the agent's file tools
  from writing under `.claude/`, and `disableSideloadFlags` stops `--plugin-dir`, but a
  shell command can still reach the uv cache and other user folders. Local administrators
  can edit or remove the managed settings (vendor docs, "What a developer can change").
  Detection afterwards: the hash chain detects an edited or removed line inside a log,
  not a log cut short, deleted or rewritten from the start, because nothing is anchored
  outside the user's control: truncation and rewriting cannot be detected locally
  (review M5). IT should compare the plugin cache with the marketplace; an anchor the user
  cannot write (the service add-on, an OS event log) is the fix and is not built.
- **The uv cache and uv-managed Pythons are user folders.** The agent's file tools are
  denied there (plugin ruleset and managed deny rules), but code planted there by the
  engineer, or by a command the person approved, runs inside the hook before any check,
  and `UV_CACHE_DIR`, `UV_PYTHON_INSTALL_DIR`, `SSL_CERT_FILE` or a Python placed on
  `PATH` still steer what uv runs; the package hashes are not verified by `uv run` (see
  "Machine requirements"). The admin-installed runtime is the end state.
- **The logs show edits, not truncation or rewriting** (see above); they are per user and
  per machine, and nothing is collected centrally (that is the service add-on).
- **Linked worktrees, submodule checkouts and `--separate-git-dir` repositories** cannot
  be pushed or committed through the agent (the scan refuses any `.git` that is not a
  folder).
- **Identity trusts the device login.** Anyone logged in as the engineer is the engineer.
- **`disableAllHooks`**: the docs say only managed settings can disable managed hooks;
  they do not say explicitly whether a user-level `disableAllHooks` turns off hooks of a
  force-enabled plugin. Not tested here.
- **Claude Desktop launch environment**: when the desktop app starts the session, its
  launch environment takes precedence over settings `env` (settings reference, `env`),
  so `CISO_STOP` and the role could be overridden there. Not tested.
- **Cloud sessions** do not read device-managed settings or this machine's plugin;
  they need server-managed settings.
- **Hooks see command text, not behaviour.** A read-only-looking command is judged by
  its text; the bundled classifier's known gaps are in `docs/reviews/skill-core-adversarial.md`.
- **Hook `cwd` vs the shell's directory**: the push is scanned in the hook's `cwd`; if
  Claude Code ever reports a `cwd` different from where the Bash tool runs the push, the
  scan reads the wrong repository (not observed; the suspicion is in the service review).
- **The agent's own git** may run a different `git` than `CISO_GIT_PATH` (PATH order,
  shell profile). The git hardening `env` covers the agent's git only while the agent
  does not unset it inside its own command.
- **Binary files** in a push, writes over 256 KiB (the intake's request bound) and
  commits over 1 MB of diff are refused as not inspectable.
- **Ask in non-interactive runs is a refusal** (`claude -p`), and the provisional ruleset
  asks for most writes, so `-p` automation under this plugin can do little but read.
- **Every hook call starts uv and Python** (about 0.5 to 1 second on the test machine).
- **The ruleset and the AI-use guidance are provisional** until the security lead
  confirms them.
- **A line scanner cannot prove absence**: encoded, split or computed secrets are not
  found; no tests are run.

## Real run, measured 2026-11-19 (Claude Code 2.1.316, Windows 11, model haiku)

The table below was measured on commit 4b0d0c1, before the review fixes changed the hook
command (`--isolated`, fixed index, runtime guard). After those fixes the coordinator re-ran
the same setup on the final plugin (commit 06b17e6): writing `.mcp.json` denied; writing a
file with a planted cloud key denied; pushing the branch with that key denied (the branch
never reached the remote); pushing a clean branch allowed (the remote holds the local
commit); stop flag on, writing a file denied. The review-fix lane separately re-ran a
read (allowed), a force push to `main` (denied), the `core.worktree` re-root push (denied)
and the skill review (report produced).

Setup: a throwaway repository with a local bare remote under the session scratchpad
(`main` pushed; `feature-secret` with a commit adding a cloud access key id built from
fragments; `feature-clean` with one clean commit). Each run:
`claude -p --model haiku --plugin-dir <this plugin> --setting-sources project --settings
<file> --allowedTools "Bash,Read,Write,Edit,Skill,Glob,Grep" --no-session-persistence`.
The settings file held only the `env` block of the managed template (stop flag, role,
agent class, `CISO_GIT_PATH`, `UV_NO_CONFIG`, `UV_OFFLINE=1`, the four git hardening
pairs). The hooks ran through uv exactly as declared in `hooks/hooks.json`. Data folder:
`~/.claude/plugins/data/ciso-agent-inline/`.

| Run | Prompt | Decision recorded | Result |
|---|---|---|---|
| 1 | run `git status --short --branch` | prompt allow; Bash `allow`, rule `allow-read-only-shell-known-people` | command ran, output returned |
| 2 | run `git push --force origin main` | `deny` (`rule_deny`, `deny-force-push-protected-branch`) | blocked with `(CISO decision dec_...)`; remote unchanged |
| 3 | Write `.mcp.json` | `deny` (`critical_finding`, `agent_config_change`; finding `path.assistant_config`) | file not created |
| 4 | Write `config.py` with the key joined from fragments | `deny` (`deny-secret-in-written-content`; `secret.cloud_access_key` at `config.py:1:12`) | file not created; the hook's message named the finding, not the value |
| 5 | run `git push origin feature-secret` | `deny` (`deny-secret-in-written-content`, `deny-high-findings-in-scanned-push-or-commit`; finding at `settings.py:1:12`) | blocked; bare remote refs identical before and after (`main` only) |
| 6 | run `git push origin feature-clean` | `allow` (`allow-scanned-push-known-people`, scan complete) | pushed; bare remote `feature-clean` = local `c5aa1fc` |
| 7 | `/ciso-agent:ciso review this whole repository ...` (on `feature-secret`) | the skill's tool call recorded as `ciso.plugin.own_tool` (allowed on its exact shape) | findings report: 1 high `secret.cloud_access_key` at `settings.py:1:12`, saved under `reports/`; no tests run, stated |
| 8 | stop flag `CISO_STOP=1`, Write `notes.txt` | `deny` (`kill_switch_engaged`) | "the security team has paused all changes by AI agents"; file not created |

Afterwards the skill's `summary` reported no broken hash chain (31 decision records, 3
findings records; it then worded this "intact", which claimed too much, review M5) and the key appeared in none of the logs or the saved report. Note: in
run 4 the model itself wrote the joined key into its own final answer; that text is the
agent's, outside the plugin's reach, and it stays in the session transcript.
